## 一、需求与设计（Requirements & design spec）

### 1. 产品结论、支持范围与用语

用户通过自然语言交付一次工作或长期安排，无需先建 Workflow、打开管理页面或先点“运行”。页面、CLI、SDK 和自然语言工具调用相同的 Host 操作契约。首批交付一次性与重复工作的完整路径；不要求完整多 Agent 编排先上线。

| 用户看到的对象 | 含义 |
| --- | --- |
| 工作安排（Automation） | 要做的事、目标、执行器、时间、停止条件和授权约定；保存后有稳定身份与版本。 |
| 一次运行（Run） | 某次计划轮次、额外运行或显式重跑；保存当时采用的约定、结果和关联执行。 |
| 执行（Execution） | 实际准备环境、检查条件、运行 agent、等待输入、停止和交付结果的共享事实；不是第二份 Automation 完成状态。 |
| 待处理事项 | 需要回答、授权、补结果或核实执行的事项；可与正在工作的进程同时存在。 |

一次性工作也有同样的历史身份，但完成后移到“历史”，不要求用户管理一个永远没有下一次时间的模板。“再跑一次”关联原工作，“改为重复”显式修改未来安排，均不覆写旧结果。

**首批入口和执行器必须分开列示：**

- 自然语言入口：Desktop Chat v3 的 Claude Code、Codex 会话；Choros 管理的终端中的 Claude Code、Codex，通过已分发 skill 和真实 CLI 操作。两条路径都必须实际验证，不能只交付 CLI 就声称 Desktop 对话已支持。
- 其他能运行 CLI 的 agent 可作为调用方，但不承诺其自动发现 skill、专用确认卡或主动消息能力。产品能力说明需明示此区别。
- 后台执行器：本规格选择现有原生 `claude-code` 与 `codex` adapters 作为首批执行路径，使用其 provider 协议事件，不从 PTY 文本猜完成。由终端 agent 创建任务，不要求后台必须使用同一终端执行方式。
- 原生路径仍需补齐规则注入、固定账号引用、运行身份、结果与恢复契约；当前代码并未完成这些保证。不能照搬同名终端 preset 的自定义命令、参数或跳过审批选项。选择不受支持的执行配置须返回 `UNSUPPORTED_EXECUTOR`，提示重新选择，不能静默换 agent。
- 首批目标：项目的新隔离 worktree，或一个明确的已有 workspace；已有无项目 session workspace 也可以被指定。不增加“每轮自动新建无项目 session”的目标选项。

### 2. 自然语言创建、确认与管理

**创建旅程：**理解工作意图 → 补齐真正缺失的信息 → 预览已解析约定 → 保存／确认执行 → 返回稳定任务与运行入口。普通问答不自动建任务。

预览必须展示名称、独立工作说明、目标、执行器与固定账号引用、时间与时区、下一批发生时间、重复和停止规则、precheck、结果入口以及权限边界。已明确的信息不重复问；“下午”“最近那个 PR”“工作日按哪里算”等歧义不能猜。名称非唯一，同名任务必须用目标和稳定 ID 消歧，不能取第一条。

| 用户意图 | 必须发生的事 |
| --- | --- |
| “建一个／先存着” | 保存为暂停；确认保存不等于授权未来持续执行。 |
| “每天九点执行” | 展示完整约定后在对话中确认启用。已解析时间、时区、目标和权限必须一并可见；不强制跳页面。 |
| 明确的“现在做一次” | 参数和授权范围已明确时可在同一操作中保存并接纳一次运行，不强制第二次按钮确认；有未确认的重要推断则先询问。 |
| “照刚才做” | 生成独立说明与必要引用，明确哪些输入每轮读取最新值；不复制全部聊天，不保存一句无法独立理解的“照刚才”。 |
| “额外跑一次” | 使用当前定义创建额外 Run，不移动原日程、不消耗计划轮次。暂停状态也允许明确的额外运行，不顺便启用。 |
| “重跑那次失败” | 创建关联原 Run 的新 Run，默认使用原定义快照并重新检查当前权限、目标、账号、setup 和 precheck；不得复用旧凭据或跳过检查。使用当前定义须另行明确选择。 |
| “改成每周一” | 预览并确认变更；修改时间、任务说明、目标、账号、权限或停止条件后，未来日程暂停，只有用户明确确认新约定才恢复。重命名不暂停。正在执行的快照不变。 |
| “上次有什么发现” | 读取现有结果；不得借查询发起新工作。 |
| “暂停／取消” | 暂停只影响未来；取消指定 Run 单独操作。含糊的“停一下”须明确当前运行、未来安排或两者。 |

未来与周期任务首次创建一律暂停。预览与启用可以在一次对话内完成；可选试跑不阻止用户直接确认启用。启用前必须已有有效时间规则、目标和执行配置，不能要求必须先有成功历史。

预览是纯读；确认绑定精确的规范化内容、版本、调用方作用域和有效期（10 分钟）。确认后内容被编辑、引用失效或版本变化时，拒绝旧确认并刷新。过期后重新展示；不得因刷新而默默把已确认的相对日期重新起算。Host 签发的预览标识证明内容绑定，不证明人真的阅读；人类确认由实际对话／UI 工具权限流程承担，不能把 agent 写出的 `confirmed: true` 宣传成新的安全隔离。

### 3. 时间规则与停止条件

所有执行时刻保存为确定 instant，同时保留原始表达、解析锚点和 IANA 时区供解释。日历计算使用任务时区，不能读取宿主本地时区替代。

| 规则 | 精确定义 |
| --- | --- |
| 立即一次 | Host 接纳运行后尽快开始；无后续轮次。 |
| 指定时间一次 | 一个明确未来 instant。输入已过期则拒绝启用；可以另行确认“现在执行”，不能悄悄改时间。 |
| 延迟一次 | 从该次意图预览接纳时刻加明确时长，只解析一次。重启或确认请求重试不重新计时。 |
| 日历周期 | 一个本地时分，可选每日、每周指定星期、每 N 天或每 N 周。保存 anchor 日期、时区及星期规则；“工作日”初期只表示周一至周五，明确不含法定调休／节假日目录。 |
| 固定间隔 | 从已确认的 startsAt 按真实经过的秒数等距产生时刻；每轮不因耗时移动下一时刻。间隔至少 60 秒。 |
| 上次结束后间隔 | 第一轮按 startsAt；前一计划轮次获得可信终态后再等待指定时长。运行未知／等待输入时不产生下一轮。间隔至少 60 秒。 |
| 连续有限轮次 | 上次结束后间隔为 0 的特例，必须有 1–100 的轮次上限；串行执行，不表达并行或跨轮结果依赖。 |

日历／间隔重复可以设置 `maxRounds`（1–10000）、排他的截止 instant `endsBefore`，或明确“持续到暂停”。同时设置上限与截止时间时先到者停止；截止只阻止新轮次，不杀已经开始的工作。无间隔、无限次数的紧密循环拒绝保存。

预览返回一次性时间或最多 5 个未来时刻；后置间隔的首轮之后取决于真实结束时间，必须显示“结束后等待 X”，不能编造绝对时间。日期未注明时区时：Desktop 提议当前设备 IANA 时区并在确认中显示；CLI/SDK 无已确认时区时要求显式提供；保存后不随设备设置变化。

高级表达式首批只支持可无损映射到上述日历规则的 RRULE 子集：`FREQ=DAILY|WEEKLY`、正整数 `INTERVAL`、WEEKLY 的非序号 `BYDAY`、单值 `BYHOUR` 与 `BYMINUTE`，可选 `BYSECOND=0`、`WKST=MO`。`DTSTART` 由明确 anchor 提供；缺少必要时分不能继承当前时间。`COUNT`、`UNTIL` 用本产品独立的轮次／截止选项表达，传入 RRULE 这些字段须拒绝并说明原因；其他字段、组合、cron、复合多时刻均返回 `UNSUPPORTED_SCHEDULE`，不忽略、不冒充支持完整 RRULE。自然语言可以继续协助转换，但转换后要重新确认。

**夏令时与时钟规则：**

- 日历时刻不存在（春季跳时）：该轮 `skipped/dst_gap`，不自动挪到另一个时间；计入轮次。
- 日历时刻重复（秋季回拨）：只取较早的 instant，一次逻辑轮次，不再运行第二个同名本地时刻。
- 显式一次性时间落在不存在或重复的本地时刻时，要求用户选择有效时间／偏移，不套用周期规则替用户猜测。
- 固定间隔按 elapsed time 运行，跨 DST 仍保持间隔；本地显示小时变化是预览中可解释的结果。
- 时钟回拨不重置已处理进度或重放轮次；向前跳视同错过时刻。时区或日程编辑只影响确认生效之后的新时刻，不回放之前的安排。
- 同一 Automation 的同一计划 instant 至多被接纳一次，不因定义版本变化再跑；DST gap 另保留本地日历槽位身份。定义版本属于输入快照，不是用来绕过去重的身份。

### 4. 轮次、失败、额外运行和修改

`maxRounds` 表示**最多安排多少个计划轮次**，不是保证成功次数。计划轮次经确定性处理后消耗名额：执行成功、执行失败、precheck 不满足、错过时刻、合并补跑中被跳过、冲突跳过均计入。主动暂停期间不生成轮次、不消耗名额。

确认卡必须写成“最多安排 6 轮；失败或跳过也计入”，不能只写“保证检查成功 6 次”。用户明确要求“成功六次”“失败一直重试到成功”时说明其属于按结果循环，首批不支持，不能静默改成六个计划轮次。

- 额外运行、对历史 Run 的显式重跑不消耗计划名额，也不改变日历、固定间隔或后置间隔的锚点。
- 常规周期中的某轮失败不自动重复该轮，也不自动停用整个安排；下一计划时刻仍按约定处理。连续零间隔批次遇到失败则暂停剩余轮次，提示处理后恢复；正常 precheck 不满足作为该轮跳过，可继续有限后续轮次。
- 前一执行未知、未确认停止或有未回答问题时保留占用。固定日程到期记录 overlap；后置间隔尚无结束锚点，不产生虚构轮次。
- 增加或减少 maxRounds 不清零已用名额；新上限小于已用名额时要求改为明确“停止后续安排”，不得隐式重置计数。已结束安排重新启用必须确认新增名额或新截止时间。
- 最后一轮已安排但还在执行时，UI 显示“无后续轮次，本轮仍在运行”，不能因为安排用完就显示工作完成。

### 5. 暂停、恢复、错过时刻与冲突

支持无限期暂停和暂停到确定 instant。自然语言“本周暂停”须展示明确的暂停结束时间；初期以任务时区下周一 00:00 为建议，取得确认后保存，不猜用户其他业务周规则。

- 手动恢复固定日历／间隔安排，从恢复之后的下一个时刻继续，暂停期间不补跑、不扣名额；原固定间隔 anchor 不变。
- 自动恢复的生效时刻是已保存的 resumeAt。Host 当时离线时，resumeAt 之后的时刻属于运行期错过，按下述规则处理；resumeAt 之前仍属于暂停，不补跑。
- 后置间隔在暂停后恢复时：没有活动轮次则从实际恢复处理时刻重新等待一个完整间隔；有活动轮次则等其可信结束后再等间隔。连续有限批次则在前轮结束且已恢复后继续。不能把恢复当成额外运行。
- 已暂停的一次性任务如果恢复时原时间已过，保留为过期未运行，要求用户明确改时间或现在执行；不在恢复动作中突然启动。

默认补跑窗口为 1 小时，可设 0（全部跳过）至 24 小时。Host 恢复时先对账活动／未知执行，再处理错过时刻。在剩余轮次和截止时间范围内，窗口内只选最近的一次合并补跑；更早的时刻记 `skipped/coalesced` 或 `skipped/missed_window`，窗口外不执行。截止后不得启动补跑。后置间隔只有一个已确定的 nextDue，不生成多轮虚拟积压。

**确定性例子：**六轮固定间隔从 09:00 每十分钟一次，Host 09:45 恢复、补跑窗口 15 分钟；09:00、09:10、09:20、09:30 均跳过，至多执行 09:40 那轮，剩下一轮 09:50。相反，若 09:00 与 09:10 已处理，用户 09:15 主动暂停、09:45 恢复，下一轮是 09:50 的第三轮，后续至 10:20 才用完六轮。

默认同一 Automation 一个活动执行，同一已有 workspace 也只能有一个执行层管理的写执行。计划冲突产生可见的 `skipped/overlap` 或 `skipped/workspace_busy`，不排无限队列。额外运行／重跑遇到占用返回 `RUN_BUSY`，不创建已接纳 Run，也不暗中等空闲后执行。用户普通终端不受操作系统文件锁约束；发现其占用或身份无法确认时拒绝复用，不能宣称该互斥就是沙箱。

### 6. 目标、账号、上下文、setup 与 precheck

**目标与会话：**

- 新 worktree：保存项目与明确的 base ref，每轮记录实际解析的 base commit，创建隔离目录。运行结束默认保留 worktree、改动和证据；移除安排不自动清理。
- 已有 workspace：精确绑定 Host/workspace 身份，不凭目录名重新匹配。路径、项目、权限失效则阻止执行；不能换到另一个同名目标。
- 会话默认 fresh。reuse 只允许指定由共享执行层管理、provider 及账号一致、已确认无活动／未知工作占用的会话；必须保存 provider session 身份并验证恢复能力。不会把 prompt 直接塞进任意现有交互终端，也不会因恢复失败自动降级成 fresh。
- 首批原生 adapter 的 resume 和身份持久捕获必须补齐后才可宣称 reuse 可用；不是直接复用目前未接通的 resume 参数。多轮默认相互独立，不隐式把上一轮全部聊天作为下一轮输入。
- 执行器型号、模型／effort 等受支持选项、provider 账号引用和权限约定固定在定义版本中。账号凭据仍由 provider 管理；不复制 token 到定义／日志。全局默认账号切换不得静默改变已保存任务的身份；原账号失效则报 `ACCOUNT_UNAVAILABLE`。
- 固定任务说明与“每轮读取最新内容”的文件／查询引用要区分，并在预览中显示。引用只在已确认目标与权限范围内解析，记录实际输入版本或可追溯标识；缺失明确失败。需要遵守的仓库规则必须经受支持入口实际注入，不能假定原生 SDK 自动加载终端的配置。

**统一执行前流程：**取得归属与占用 → 目标准备 → 必要 setup → 可选 precheck → agent 工作。额外运行和重跑完全相同。此流程由共享执行路径负责，Automation 不另写一套启动器。

- 新 worktree 必须运行现有规则解析出的 setup；未配置与配置无效是不同结果。确实无 setup 时可继续，无效配置、启动失败、非零退出、超时或状态未知都不得启动 agent。
- 已有 workspace 在确认中明确选择“每轮运行 setup”或“使用已准备环境”。后者不伪造 setup 成功；若任务依赖 setup，必须选择前者。
- setup 使用现有配置源优先级和 cwd 规则，记录实际命令来源／版本；默认超时 10 分钟，可在任务约定中显式调整。超时先请求停止，未确认静止则保留占用和待核实。
- precheck 是任务约定中的独立轻量 shell 检查，不悄悄写入仓库 setup 配置。默认在本次 workspace、setup 之后执行；不提供新 worktree 创建前的另一套 precheck 语义。它可能已经产生准备成本，确认中须明确。
- precheck 默认超时 30 秒，允许 1–300 秒。退出 0 才进入 agent；正常非零为 `skipped/precheck_false`，超时、无法启动等为失败；保存退出码与有界输出。它是代码执行，不是安全的纯表达式，权限同样受确认约束。
- setup/precheck 和 agent 均有稳定的本次操作身份与回执。重启后不能无条件重跑未知 shell 操作；保守进入待核实，不用潜在副作用换取表面的“自动恢复”。

### 7. 完成、待处理、取消和恢复

完成结果至少包含：结论摘要、agent 自报成功／失败、产物或改动引用、验证证据或明确的未验证说明。报告结构有效不等于内容真实；需要测试或人工 review 的工作，必须据其明确输出契约表达是否满足，不能自动标成用户已接受。

**三个事实独立保存并展示：**agent 的工作报告、Host/provider 观察到的执行事实、用户的接受／已读状态。原生 turn 完成可以证明该回合结束，不能单独证明业务目标达成。不得将 PTY Stop、Attached、终端退出、SDK 启动成功或模型一句“好了”统一解释为成功。

报告必须由当前绑定的执行／provider session／turn 通道提交，最小结构由服务校验；成功结算要求报告符合输出约定、没有未处理问题，且对应执行已获可信结束／静止证据。收到报告但执行仍活动时显示“已提交结果，仍在结束”；无错误的回合结束但缺少有效报告时显示 `needs_result`，保留已有输出供人工检查，不制造成功。provider 明确失败或准备阶段异常可以根据可信错误结算 failed，不强求失败的 agent 再写报告；停止事实仍不明确时继续保留占用与待核实。UI 中“已完成”必须能展开看到结果来源和验证状态。

结果提交的最小契约如下；执行／session／turn 的来源绑定由服务依据受控通道确定，不能仅信任调用方自填的 ID：

| 字段 | 约束 |
| --- | --- |
| `requestId`、`executionId`、`expectedVersion` | 当前执行范围的幂等身份与版本；旧执行或其他来源不能结算本次工作。 |
| `report.outcome` | `completed` 或 `failed`，表示 agent 对工作目标的自报，不表示用户接受。 |
| `report.summary` | 非空结果摘要；不能仅用进程退出码代替。 |
| `report.artifacts` | 产物引用数组，可为空；引用携带类型、定位、长度／校验和或明确的可变／缺失标记。 |
| `report.verification` | 明确 `not_run` 及原因，或提供验证命令／方法、结果和证据引用。UI 区分 agent 提供的证据与 Host 实际观察的验证，不把自报升级成独立验证。 |

相同请求和同一结果重复提交返回原回执；冲突报告拒绝且保留已提交结果。超大或不符合结构的报告返回明确错误，不截断后伪装有效；正常回合结束时仍无有效报告则进入 needs_result，可信失败与取消仍按各自规则处理。运行等待输入不靠把 outcome 写成 completed 来表达，必须使用持久问题入口。

当前首批 adapter 需要真实可调用的结果提交和请求输入能力。权限请求沿原生审批通道，业务问题沿共享执行的持久问题入口，均有问题身份、版本和答案记录。等待默认不超时批准、不自动重试；持续可见并保留必要占用，用户可以回答、拒绝或取消。重启后若原 provider 请求仍可核实则恢复原请求；无法恢复时保持待核实，而不是把旧“允许”消费到新请求。自动任务不加载管理其他 Automation 的特权工具作为默认工作能力。

取消接纳与停止事实分开。取消先禁止后续启动步骤，再中断归属明确的 provider turn／准备进程；只有证据足以确认对应写执行静止才显示 cancelled 并释放占用。取消与完成并发以持久提交顺序裁决：完成先结算则返回已完成；取消先接纳则迟到报告可保留为证据，不能抹去取消意图。进程或子进程停止不明时保留 `stop_unconfirmed`，不因收到了“已发信号”就宣布成功。

Host 重启首先对账存量执行，再开启新触发。仍存活的原执行继续观察；已结束且结果可核实则补记；确认从未执行才可推进原操作；其他情况为 `unknown`。用户可查看证据、重新核实或请求停止，不能通过“强行标失败”释放可能还在写入的工作并启动冲突重跑。若后台 session 不存活，恢复聊天上下文不自动等于重发原任务；不能证明续接安全时要求人工处理。

### 8. 结果交付、管理页面与 Profile

持久 Run 详情是结果权威，默认交付位置为 Automation 运行历史。对话中的“上次结果”读取这里。Desktop 对完成、失败和待处理事项使用现有通知外观；普通 skipped 在历史可查，不逐条弹窗。通知被 OS 拒绝或 Desktop 关闭时，历史和待处理记录仍在，不承诺 OS 最终送达。

首批不主动向已关闭或仍工作的原会话注入 prompt。原对话保存来源引用，用户可以询问结果；若以后支持结果回投，必须是只追加展示、不启动 agent 的独立操作，不拿现有 chat `prompt` 冒充通知。外部终端客户端不承诺主动回投。

建议的页面结构（不是新增视觉系统）：

```text
Automations                        新建
安排 / 运行历史 / 待处理            搜索、状态筛选
名称          时间与时区       下一次       最近结果
每日巡检      周一至五 09:00   周二 09:00   有 2 项发现
一次依赖检查  一次性           无           已完成·未验证

运行详情
工作约定快照 · 触发来源 · 计划/实际时间
准备 → setup → precheck → agent → 结果
摘要 / 产物与diff / 验证 / 错误与待处理
打开workspace、会话；回答、取消、明确重跑
```

- 列表区分安排状态与本轮执行状态；可筛选成功、失败、跳过、待处理及历史。一次性已结束项默认在历史中，仍可再跑或转为重复。
- 修改、暂停、启用、归档、回答和取消只调用 Host 命令；客户端不乐观伪造执行成功。新建表单与自然语言使用同一预览结果。
- 首屏取得一致的快照与事件游标，增量按游标消费；断线补读，游标过期重新取快照。页面重复订阅不重复派发。
- 自动化不新增独立 Profile 成员类型：新 worktree 目标继承项目 Profile；已有 workspace 继承其项目或独立 session 的 Profile。Host 和 CLI 不接受 renderer 当前 Profile 作为执行权限或隐式目标。
- 默认列表跟随当前 Profile；跨 Profile 待处理摘要始终可发现，点击先定位所属 Profile 再打开 Run。一个 workspace 的多项 Automation 待处理按执行／问题身份计数，不套用现有终端 workspace 去重后丢失事项。
- 移动项目或 session 时其安排与历史随归属展示；目标被删除或无法解析时不丢记录，停止未来派发并进入可访问的全局“目标失效”待处理列表，不猜另一目标。来源会话删除不删除结果。
- 归档安排会暂停未来触发并保留历史、当前执行与文件；取消当前执行仍需单独操作。不提供本阶段的自动 worktree／产物清理。

### 9. 领域数据、操作契约与幂等

Host 是安排、轮次、执行与待处理的权威；复用本机持久化，不把新增记录存 renderer localStorage，不建立新远程服务。现有 chat journal 保存 provider transcript；共享执行通过稳定引用关联它，不把 transcript 全量复制到 Automation，也不再存一份互相竞争的完成状态。物理表划分和包结构留给实施计划。

必须持久表达：定义及不可变版本、解析时间规则及进度、每次触发身份与采用的快照、共享执行和准备操作身份、provider session/turn 关联、结果／证据、问题与答案、取消意图、幂等命令回执和可续读的变化序号。

下面是**新增契约**，不是声称目前已有这些 API。所有写操作携带 `requestId`；相同调用方作用域、相同 ID、相同规范化参数返回原回执，不重复副作用；同 ID 不同参数拒绝。修改定义、启停、归档和回答携带 `expectedVersion`，冲突刷新后重试，不覆盖。

| Host 契约 | 行为 |
| --- | --- |
| `automations.capabilities` | 返回真实入口／执行器、规则子集与边界，供所有客户端准确展示。 |
| `automations.preview` | 纯读规范化输入、校验引用与时间、产生工作约定摘要及短期确认标识；不创建真实任务。 |
| `automations.create` / `update` | 消费确认过的定义；新建暂停，实质修改使未来安排暂停。明确立即一次可在同一接纳事务内创建 Run，复用相同执行路径。 |
| `automations.setScheduleState` | 明确启用、暂停、暂停至指定时间或恢复；启用绑定当前定义确认，返回下一次时间或结束原因。 |
| `automations.runNow` / `retryRun` | 创建新的 Run；前者使用当前版本，后者绑定原 Run 快照，始终检查当前权限和占用。 |
| `automations.archive` | 保留历史与活动执行，不删除文件。 |
| `automations.get` / `list` / `getRun` / `listRuns` / `readEvents` | 分页快照与结果读取；返回结构化原因，不靠翻译文案分类。 |
| 共享执行 `requestCancel` / `requestInput` / `answerInput` / `reportResult` / `reconcile` | 操作当前归属的执行；报告与问题的写权限绑定对应执行来源，不采用公开终端 hook 作为授权。 |

示例是尚未实施的规范化定义，不会创建实际任务；账号引用仅为示例标识：

```json
{
  "name": "构建状态检查",
  "instructions": "检查目标项目的构建状态，只生成摘要，不修改代码或发布评论。",
  "target": {"kind": "newWorktree", "projectId": "b3a47143-fcbd-483d-927c-dd62d0458b7b", "baseRef": "origin/main"},
  "executor": {"harness": "claude-code", "accountRef": "profile-work", "sessionMode": "fresh"},
  "schedule": {"kind": "fixedInterval", "startsAt": "2026-09-29T01:00:00Z", "intervalSeconds": 600, "timeZone": "Asia/Shanghai"},
  "stop": {"maxRounds": 6},
  "missedRunWindowSeconds": 3600
}
```

接纳返回 Automation ID、定义版本、安排状态、确定的下一次时间／相对规则、确认摘要和可定位的 Run ID（若本次创建并运行）；返回已接纳不表示 agent 已启动。CLI 命令提供同语义的 create/update/enable/pause/resume/run/retry/cancel/archive/list/runs/show/preview；支持 JSON 与 prompt 文件输入，不能把用户多行工作说明不安全地拼接进 shell。skill 使用实际 `choros` 命令，删除 Superset、远程 host 与强制试跑等未支持承诺。

触发领取、轮次计数、执行归属和创建意图必须在可串行化的短事务边界内一致；事务外才进行 provider／shell／Git 操作。定义 revision 不参与绕过去重；手动 requestId 与计划 occurrence 身份分开。跨 Host DB 和 chat journal 不假装有原子事务：必须可按稳定操作身份查回原动作，缺少回执时对账，不能换 ID 重发。

### 10. 非功能要求

- 正常运行、无休眠和资源故障的本机 Host，到期 5 秒内接纳触发或记录跳过；不将此目标表述成 agent 五秒内完成启动。API 的接纳请求不等待 setup 或 agent 结束。
- Run 列表和事件读取默认 50 条、最多 100 条，带稳定游标。长期离线产生的大量未执行时刻允许按区间保存精确 skipped 汇总，明确范围／次数／规则快照并提供分页详情；汇总不是一次真实执行，绝不合并已执行 Run 的证据。
- 历史不因编辑／归档自动删除；正文与输出有界。单次结果报告最多 64 KiB，setup/precheck 展示输出每阶段最多 64 KiB，超出明确标记截断；大型证据以受控文件引用、长度和校验和保存，缺失／变更须标记，不能把可变 workspace 路径当不可变证据。
- 新增命令保持本机 Host 认证和文件保护边界；默认不输出凭据、确认能力、完整 prompt 或问题正文到运维日志。文件、数据库或通知失败不得伪装完成；数据库不可写时停止接纳新执行。
- UI 使用 Lingui 显式 ID 和全部发布语言，按任务时区展示日期；不使用只有颜色的状态。表单、确认、回答与取消支持键盘、焦点恢复和状态播报；OS 通知不能替代页面可见结果。
- 不因 Automation 自动启用 provider 的 bypass/skip-permissions 或提高权限。仅有“只读”文字不是沙箱；无法证明允许的动作必须沿原生授权流程等待或拒绝，不能后台自动批准。

### 11. 明确不在本阶段范围

完整 DAG／多 Agent Workflow、自然语言自动拆解团队、结果驱动循环、事件/Webhook 触发、远程调度／迁移、托管执行、法定节假日目录、完整 cron/RRULE、任意自定义 PTY agent 的可靠后台执行、每轮新建无项目 session、自动向原对话投递新 prompt、自动合并／发布及自动删除 worktree。

#37 的已保存多节点 Workflow 调用及高级时间语法未全部覆盖，#36 的并行、依赖与交接未交付；完成本规格不能将两个 Issue 全部标记完成。后续 Workflow 必须复用本次执行与结果契约，不复制一套 agent 完成状态。

已读根 AGENTS、Desktop 持久化规则和 `docs/agent-tooling.md` 中 provider 账号边界，并核对 Host 认证与当前 public lifecycle hook。未发现独立、完整的组织安全政策，需安全负责人或技术负责人确认。风险包括自然语言授权范围、prompt injection、执行结果来源、共享本机身份、账号固定及停止证据；Profile 和 worktree 都不构成权限沙箱。当前用户的 agent 可能拥有同一 OS 用户的文件访问权，本规格不声称通过一个本地确认标识消除这种风险。

### 合规与隐私（Compliance）

不新增支付、组织权限或云同步。工作说明、报告和上下文仍可能含个人／业务数据；不复制无关对话，不将账号凭据写入任务；执行时使用 provider 仍可能向现有服务传输输入，不能把“本机调度”说成“数据绝不出设备”。未发现独立隐私／合规政策，需负责人确认保留、删除和 provider 使用边界；不宣称已通过 GDPR/SOC2 等审核。

### 用户体验与无障碍（UX）

已读 Desktop AGENTS、redesign 和 `packages/i18n/README.md`。实体与历史不进入 renderer localStorage；使用既有组件、Lingui 和日期格式约定。自然语言与可访问的表单等效，状态可解释，取消不假装停止，信息缺失明确提示。尚未进行真实 Desktop 验证，实施后需要实际页面、对话、键盘、通知和跨 Profile 场景证据，不能用静态检查替代。

## 五、需人工复核的风险（Areas of concern）

- **轮次与时间产品语义（负责人：产品负责人 xchunzhao）**：第3–5节的取舍已随本规格接受；按计划机会计数不保证成功次数，主动暂停不计数、离线跳过计数，实施时仍需让确认内容准确可理解。
- **首批执行器选择（负责人：产品负责人／技术负责人）**：原生Claude/Codex作为首批执行器的范围已随本规格接受；不承诺所有终端preset。自然语言调用入口不因此限为某一种模型，具体能力接入与证明在plan中落实。
- **持久化与跨数据库恢复（负责人：技术负责人）**：Host DB、chat journal与外部进程之间没有天然原子事务；稳定身份、回执丢失对账及现有resume缺口需要真实故障注入证明。只加outbox或mock调用次数不算完成。
- **授权与秘密／结果信任（负责人：安全负责人；未指定时由技术负责人承担）**：未加载到独立安全政策。原生规则注入、账号固定、管理工具暴露、报告绑定、prompt injection及公开hook边界需要专门审查。不能把用户态agent与Host描述成互不信任的强隔离主体。
- **取消和旧setup路径（负责人：技术负责人）**：现有warning后启动、取消API过早disposed及daemon停止证据不足需正向修正；不能在新功能里用额外分支掩盖共享路径的契约缺口，亦不得改变无关会话行为。
- **数据保留与provider使用（负责人：隐私／合规负责人；未指定时由技术负责人协调）**：没有独立合规政策可据以宣称通过；需确认任务和证据保留、删除责任及外部provider输入边界。
- **自然语言确认、Profile和无障碍（负责人：设计负责人）**：不能把现有泛化tool approval直接当完整工作约定确认；跨档attention也不能依靠仅终端来源的计数。需真实产品场景验收。
- **长期运行与支持范围（负责人：技术负责人／产品负责人）**：本机休眠、后代进程和provider版本限制必须明确；若某adapter无法证明恢复或停止，需解决能力缺口或重新评审范围，不得以静默降级交付。

xchunzhao 负责协调上述角色的实际复核人。产品规格现已接受；独立安全／合规／技术签核未另行记录，不虚构额外审批。涉及迁移、执行身份及公共API，风险处置与实施证据继续受plan及高风险变更门槛约束。
