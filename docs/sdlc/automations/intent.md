# 需求意图：用自然语言委托一次性与重复执行的工作

> 本轮评审的是用户结果、产品范围和约束，不是数据库设计或引擎选型。本文尚未接受；对话中的方向认可和“继续”不代替本文件及后续 spec、plan 的独立审批。文中的任务示例不构成创建或启用真实任务的指令。

## 要解决的问题（Problem）

用户希望把一件事交给 Choros，在现在、以后某个时间或约定的节奏执行，之后能找回结果，而不必反复解释、记着时间、重新开会话并翻终端。现有 Automation skill 和 CLI 帮助文字让人以为已经具备这种能力，但本轮核对的 v0.1.6 CLI 没有 automations 命令；skill 仍引用 Superset 的创建、运行和日志命令。操作说明不等于实际存在的调度与任务管理能力。

用户在本次讨论中明确纠正了以按钮为中心的描述：

> “我觉得不是用户点击运行。”
>
> “Automation 应该是说，用户可以通过自然语言触发它创建一个任务，比如说定时任务，这也算是 automation 的一种。”

用户同时要求覆盖“定时任务”“跑一次”“重复跑”。因此，产品起点应是自然语言委托工作，而不是要求用户先理解 Workflow、手写时间表达式或进入管理页面点击运行。

依据与边界：

- [Issue #37：Automations](https://github.com/tekton-ai/choros/issues/37) 提出了定时执行、precheck、运行历史及恢复等需求，目前仍是待实施提案。
- [Issue #36：Agent Workflow](https://github.com/tekton-ai/choros/issues/36) 及其评论提出共享执行、结果与恢复模型，不是已接受的技术规格。
- [Discussion #23](https://github.com/tekton-ai/choros/discussions/23) 是 Workflow 动机与候选参考的 brainstorming，不代表已选择 Tutti、UWF 或其他引擎。
- 本文把自然语言入口和一次性、有限重复工作纳入待评审范围。它不是对 #37 原有范围的静默替换，也不以单任务路径交付冒充两个 Issue 全部完成。

## 希望用户得到的结果（Proposed outcome）

用户可以在 Choros 内受支持的对话中说明“做什么、什么时候做、做几次或何时停止、在哪里做、交付什么”。Choros 将其整理成用户能理解和确认的工作约定；取得必要授权后，工作不依赖原对话持续打开。用户回来时能直接知道结果、失败或跳过原因，以及什么需要自己处理，也能继续用自然语言调整或停止后续执行。

### 用户如何交付工作

| 入口 | 用户示例 | 用户希望得到的结果 |
| --- | --- | --- |
| 从自然语言新建 | “明天下午三点检查这个 PR 的状态，给我一份摘要。” | 保存明确的一次性工作约定，到期执行，结果可找回。 |
| 保存刚完成的工作方式 | “刚才这套检查，以后每个工作日做一次。” | 把可重复的工作说明保存下来，不要求每天重新解释，也不依赖“刚才”指向的临时聊天上下文。 |
| 调用已有任务 | “把每日巡检现在额外跑一次。” | 在原任务下产生一次可追踪的额外执行，不暗中移动原有日程。 |
| 管理已有任务 | “改成每周一。”“本周先暂停。”“取消正在跑的这一轮。” | 准确定位并修改对应对象，区分未来安排与当前执行，不影响无关任务。 |
| 页面、CLI 或 SDK | 用户查看任务列表，或通过已有工具链管理任务。 | 操作同一批任务、看到同一份结果；这些入口不是自然语言创建的前置步骤。 |

普通问答不自动转成后台任务。只有用户表达了委托执行、安排未来工作、重复执行或保存工作方式的意图，才进入 Automation 创建或管理流程；不把每条聊天消息都建成一个 Automation。

### 什么时候做、做几次

“定时”和“重复”不是互斥类型：明天九点执行一次，是定时且一次性；每天九点执行，是定时且重复。以下是面向用户的场景分类，而不是要求用户选择的一组底层枚举。

| 首批建议覆盖的场景 | 用户示例 | 结果边界 |
| --- | --- | --- |
| 立即执行一次 | “现在在后台检查这个仓库的依赖，完成后给我报告。” | 授权后开始，结束后保留结果，不自动安排下一轮。 |
| 延迟或指定时间执行一次 | “两小时后检查一次。”“明天下午三点生成汇总。” | 固定明确的执行时间，只执行一次；重启不能重新起算同一个“两小时后”。 |
| 按日历周期执行 | “每个工作日早上九点检查新 Issue。” | 按确认的时区和日历规则重复，不随宿主时区悄悄改变。 |
| 按间隔重复执行 | “每隔两小时检查一次构建状态。” | 明确间隔的起算方式；上一轮未结束时不悄悄叠加新的写入工作。 |
| 有限重复 | “每十分钟检查一次，一共六次。”“每天生成报告，到周五为止。” | 次数或期限到达后停止，无需用户回来手动关闭。没有时间间隔的“连续跑三轮”应说明各轮是否等待上一轮结束。 |

按结果重复（例如“每五分钟看一次 CI，结束就告诉我，最多等一小时”）与事件触发（例如“出现新 PR 时审查”）列为候选扩展，不在本草案的首批承诺中。失败重试也不等于计划中的下一轮，不能混作同一种“重复”。

### 自然语言创建后的完整体验

1. **得到可读的工作约定，而不是只收到“好的”。** 用户能看到任务名称、工作内容与目标、执行时间和时区、重复与停止条件、agent 选择、结果交付位置，以及会发生的写入行为。已明确的信息无需重复追问；影响执行的歧义不能靠猜测填入。
2. **保存与开始执行是不同授权。** “帮我建一个”不自动理解为“立即启用持续运行”。未来与周期任务先保存为暂停状态，再在对话中确认启用；无需强制跳转页面。对于明确授权的“现在做一次”，创建与本次执行可以在同一对话完成。手动试跑是可选检查手段，不是所有任务创建的必经步骤。
3. **能区分一个长期安排与它的每次执行。** “每日巡检”可以持续存在，今天的成功、昨天的失败和一次额外运行分别保留。修改未来安排不改写过去的工作约定和结果；额外运行是否消耗有限次数，需要在规格阶段明确。
4. **不需要靠翻终端才能知道发生了什么。** 结果至少能表达做了什么、结论、产物或改动引用、验证证据或未验证说明。未启动、失败、跳过、等待用户和待核实不能被统一展示成“完成”。具体通知载体不在本文定死。
5. **自然语言管理同样可靠。** 同名或多候选任务要先消歧；“暂停以后运行”和“取消当前这一轮”不能混为一谈。移除任务安排默认不删除已有结果、workspace 或用户改动。

### 建议的第一条用户旅程

用户先说：“每个工作日早上九点检查 Choros 仓库的新 Issue，只整理摘要，不发评论。”系统呈现目标仓库、完整检查说明、确认后的时区与下一次时间、持续重复直到暂停、只读范围和结果入口。用户可在对话中修改、仅保存或明确启用；不要求先点击一次运行。启用后，用户离开页面也不影响本机可用期间的到期执行。

用户随后说“现在额外跑一次”，应得到该任务的一次独立执行；再说“本周暂停”，系统应明确暂停期限和恢复安排，不能把含糊时间当成永久暂停或猜测恢复时刻。用户回来问“上次有什么发现”，应能直接读取对应结果，而不是重新启动检查。

## 影响的用户与系统（Affected users and systems）

首批面向在本机使用 Choros、需要巡检、Issue 整理、报告或其他可委托 Agent 工作的个人用户。任务可作用于指定项目或已有 workspace；是否把无项目的新建会话作为完整创建选项，留待范围评审，不因当前讨论会话没有项目就默认扩展。

影响面包括：

- Choros 对话中的 Automation 操作入口及 `plugins/choros/skills/automate/` 指引。
- Desktop 的任务管理与结果展示；现有 Profile 下的归属和跨 Profile 待处理提示需要在规格中明确。
- `packages/cli/` 及对应 SDK 能力：自然语言和其他入口共享行为，不继续暴露不可执行的示例。
- `packages/host-service/`：本机任务管理、时间触发、执行记录与既有 workspace、setup、agent、PTY 能力的衔接。

本文不承诺所有外部 Agent 客户端天然具有相同工具，也不新增一套供 Automation 专用的聊天模型或执行宿主。

## 必须遵守的约束（Constraints）

### 用户授权与数据

- 自然语言是意图入口，不是绕过登录、权限、仓库规则或人工批准的通道。创建、启用任务不授予超出其已确认范围的写入能力；worktree 隔离不是安全沙箱。
- 保存“刚才的工作”时，要提取独立可执行的说明和必要输入或引用，不无差别复制整段聊天、秘密和无关个人信息。依赖的上下文不可用时明确说明，不能静默补造。
- 需要回答或授权时应保留待处理事项并让用户找得到；不得因无人在线自动批准。agent 自报完成、验证通过和用户接受是不同事实。
- 暂停阻止后续触发；取消当前运行是独立动作。未确认执行已经停止时，不能显示已取消或允许冲突写入。

### 本机执行与可靠性

- 初期仅承诺本机 Host 正在运行且机器可用时执行。关闭对话或管理页面不应停止已接纳的任务，但关机、休眠或 Host 退出期间不承诺照常运行。
- 错过时刻要有可见处置，恢复后不无界回放积压。窗口内至多合并补跑一次、窗口外跳过的既有 #37 方向保留，具体窗口和各类任务行为由 spec 明确。
- 重复触发、请求重试和 Host 重启不能造成同一次工作重复启动。无法确认的执行保留待核实，不把连接丢失当作失败后自动重跑；不承诺外部副作用 exactly-once。
- 默认同一 Automation 不重叠执行；不同任务使用同一个已有 workspace 时也需要可见的冲突处理，不能把后续 prompt 注入仍在工作的 agent。
- 必要 setup 未成功不得启动 agent。可选 precheck 只有通过才进入 agent 执行；正常不满足条件、超时和执行异常必须可区分。额外运行与失败重跑不能隐式绕过 precheck。
- 日期、时区、间隔、有限次数必须被准确表达。未支持的时间表达或模糊的日历语义应说明限制或请求澄清，不能静默降级；不默认把“工作日”解释为具备各地法定节假日知识。

### 与 Workflow 的边界及不做事项

- 不要求用户先创建 Workflow，也不把完整多 Agent Workflow 作为一次性与重复工作交付的前置条件。
- 运行身份、结果、取消与恢复使用共享执行能力，不在 Automation 内再建一套竞争的 agent 完成状态；单 prompt 与后续多节点执行应沿同一契约衔接。本文不预选包名、表结构、引擎供应方或具体状态枚举。
- 首批聚焦单项 Agent 工作的完整用户路径。#37 中已保存 Workflow 的定时调用仍是后续范围，尚未交付时不得关闭其全部验收；#36 的依赖、并行汇合、交接与审批也不因共用执行基础而算完成。
- 不包含通用 BPMN、可视化流程编排器、远程调度或故障迁移、托管算力、任意业务连接器、Webhook 平台以及默认自动合并或发布。
- 本阶段只形成意图草案，不创建真实 Automation、不启用定时任务、不发布 GitHub Issue/comment，也不越过后续规格和实施计划审批。

## 需要在后续规格中回答的问题（Open questions）

下列推荐项是评审输入，不是已接受的规则；规格阶段须逐项作出明确决定。

1. **自然语言入口覆盖哪些会话？** Choros 内置会话和外部终端 Agent 分别通过什么受支持的操作入口完成创建、确认和管理？不能只交付其中一种却声称全部可用。
2. **一次性任务的保存方式是什么？** 建议只产生一次工作约定与历史，不让用户被迫长期管理一个无下一次时间的模板；应允许之后显式“再跑一次”或“改为重复”。这一产品呈现是否合适？
3. **时间理解与确认如何处理？** 默认时区从哪里来？“明天”的解析锚点、“工作日”的含义、含糊时间、DST 跳变和重复时刻、时钟回拨、修改日程的生效边界分别如何解释和展示？
4. **重复与停止如何计数？** 固定间隔和“上次完成后间隔”都支持吗？没有间隔的连续多轮怎样限制？有限次数按计划机会、实际启动还是成功执行计数？跳过、失败、额外运行、重跑和修改截止时间怎样影响剩余次数？
5. **暂停、恢复和错过时刻如何衔接？** 是否首批支持“暂停到某一天后自动恢复”？用户主动暂停期间是否排除补跑？一次性过期任务如何处理，什么场景允许窗口内补跑？
6. **结果怎么交付和提醒？** 建议持久运行详情作为可查询的结果来源，对话负责定位与摘要；Desktop 通知、原对话回投和跨 Profile 提醒各覆盖哪些情况？不假定外部客户端能接收主动消息。
7. **目标、会话和上下文如何选择？** 新隔离 worktree 与已有 workspace 如何呈现？无项目任务是否纳入首批？已有会话的 fresh/reuse、可变输入来源与固定说明怎么让用户明确确认？precheck 在什么目录、在准备目标的哪个阶段运行？
8. **完成与无人值守边界是什么？** 每种受支持 agent 如何给出绑定本次执行的结果，缺失报告如何呈现？等待用户多久、占用如何处理、验证与接受怎样区分？默认不自动重试状态未知的执行，也不自动批准权限请求。
9. **候选扩展是否另立范围？** 事件触发、按结果停止的循环、已保存多节点 Workflow 定时调用分别何时纳入？首批发布须清楚说明支持范围，不在 UI/skill 中提前承诺。
