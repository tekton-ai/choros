# 需求意图：工作档案（Work Profiles）

> **本轮评审重点：这个功能是否解决了真实问题、范围是否准确、约束是否可接受。**
> 本文说明“为什么做、做哪些、不做哪些”。具体交互和验收标准在 `spec.md` 中确定，技术实施步骤在 `plan.md` 中确定。

**范围修订（2026-09-07）：** 负责人已明确要求，Work Profiles 只基于最新 `main` 现有的功能实现，不恢复已移除的 Superset 功能。本次核对的基线是 `origin/main` 的 `527ec4ea1`。

本修订稿替代此前按组织划分、支持多 Host 的需求意图。当前状态仍为 `draft`（草稿）；人工接受后，才重写下游的需求规格和实施计划。

## 要解决什么问题

Choros 目前把项目、独立会话（不属于项目的 Session）和工作区放在一起展示，缺少更高一层的工作分类。

当一个人同时处理几类彼此独立的工作时，只能靠自己在脑中区分它们。这既影响专注，也容易在错误的工作类别下打开或创建内容。个人事务和公司工作只是两个例子，分类应由用户自行定义，而不是产品预设。

这不是推测出来的需求：发起人在自己使用 Choros、试图区分不相关的工作时，直接反馈了这个问题。

## 希望用户得到什么结果

用户可以创建并命名多个工作档案（下文称 Profile），分别管理不同类别的项目和独立会话，并且始终知道当前正在使用哪个 Profile。

用户只看到和操作当前 Profile 下的项目、会话和工作区，可以快速切换到另一类工作。切换时，各自的工作状态保留下来；新建内容归到用户预期的 Profile。用户也可以重命名 Profile，调整项目和独立会话的归属。

## 影响谁、影响哪些功能

首批面向使用 Choros Desktop 处理两类或更多独立工作的个人用户，不限制这些工作的名称或分类方式。

**本次覆盖最新 `main` 已有的以下功能：**

- 侧栏，以及项目、独立会话和工作区的导航。
- 工作区列表、Pull Requests（PR）。
- 搜索、命令面板、最近访问和历史导航。
- 现有的项目与工作区创建、导入流程，包括全页创建和快速创建入口。
- Desktop 内的 Profile 管理界面：命名 Profile，分配项目和独立会话。

**保持全局、不随 Profile 筛选的功能：** 设置和插件。它们仍属于整个 Desktop 安装实例，切换 Profile 不改变其数据或行为。

**本次不包含：** Tasks、Automations、Pages、组织管理、V1/V2 模式开关、远程多 Host 管理、Mobile 和 Web 管理应用。不会为了满足旧版 Work Profiles 文档而恢复已经移除的产品模块。

## 必须遵守的约束

- **以最新 `main` 为准。** 只针对当前本地 Desktop 产品，沿用现有能力和对象标识规则，不重建旧 Superset 架构。
- **已有工作不能丢失。** 升级后，现有项目、独立会话和工作区都必须仍可访问。
- **升级后的归属清晰。** 现有工作出现在明确标识的 `Default` Profile 中，让用户仍能理解并继续使用升级前的工作内容。
- **不是权限隔离。** 第一版 Profile 不新增权限或授权边界。
- **离线可用。** 第一版不新增云存储、云同步服务，也不让 Profile 依赖云端在线。数据和功能必须能在离线时使用。
- **不依赖远程功能开关。** 不为此功能新增或依赖远程 feature flag。
- **不承诺跨设备一致。** 第一版不保证不同设备上的 Profile 名称和成员归属保持一致。
- **一个 Desktop 安装实例只有一份本地 Profile 注册表。** 所有窗口共享 Profile 定义和归属；不依赖当前组织、按账号划分的命名空间或远程 Host 发现。
- **沿用本地 Host 的对象标识。** 项目和独立会话来自现有本地 Host。项目标识沿用当前产品的规则，不引入按仓库 URL 合并项目的规则，也不承诺跨设备标识一致。
- **数据归属边界不变。** Desktop 管理 Profile 状态；本地 Host 继续管理项目、工作区和运行中的进程，不存储或同步 Profile 数据。
- **不给未来扩展设障碍，但本次不做同步。** 本地模型不应阻碍将来通过用户自有 GitHub 仓库实现可选存储或同步；该集成不属于第一版。

## 需要在新版需求规格中落实的问题

- 滑动手势应该在哪个区域生效？点击和键盘操作如何提供等效的 Profile 切换能力？
- 非当前 Profile 中的通知、运行状态和待输入请求如何保持可见，又不把它们的工作内容混入当前视图？
- 哪些 Profile 管理操作需要具备导入、导出的底层能力，才能在将来接入 GitHub 仓库存储时不改变用户理解的行为？

## 修订后仍保留的产品决定

- **归属唯一。** 每个项目、独立会话只属于一个 Profile。未明确分类的对象属于 `Default`；移动到另一个 Profile 是改变唯一归属，不是再添加一个标签。
- **工作区继承项目归属。** 项目下的工作区不能单独分类。终端会话、聊天会话、agent 会话和 PR 继承所属工作区或项目的 Profile。
- **普通工作界面只显示当前 Profile。** 跨 Profile 汇总仅用于 Profile 管理，以及待处理事项和通知摘要。
- **切换保留工作状态。** 从工作区切换 Profile 时，打开目标 Profile 上次使用的工作区；如果没有使用记录，则显示该 Profile 的空状态。支持 Profile 的列表页面保持当前路由，只更换展示内容。设置和插件不受影响。原 Profile 中的终端、agent 等工作继续在后台运行。
- **窗口独立选择。** 窗口之间共享 Profile 定义和成员归属，但各自选择当前 Profile；一个窗口切换，不强制其他窗口跟着切换。
- **后台提醒不能消失。** 非当前 Profile 的待处理事项仍可被发现。点击通知时，先切换到其所属 Profile，再打开工作区。
- **Default 始终保留。** 内置 `Default` 可以重命名，但仍是内部默认 Profile，不能删除。空的自建 Profile 可以直接删除；非空 Profile 只能通过“全部移至 Default 后删除”（`Move all to Default and delete`）操作，先重新分配全部内容，再删除 Profile。
- **新建内容使用提交时的归属。** 从当前 Profile 新建的项目或独立会话自动归入该 Profile，导入和快速创建也一样。创建尚未完成时即使切换 Profile，也以提交时捕获的 Profile 为准。归属写入失败时，不删除已创建的工作；内容保留在 Default，并提供恢复到目标 Profile 的操作。
- **重新打开不等于重新分类。** 重新打开或设置已有项目时保留原归属，不隐式移动。没有当前 Profile 上下文的新建对象归入 Default。在项目下创建工作区，不改变父项目的归属。
